#### 表关联优化：

小表驱动大表
 如果明确知道哪张表是小表，可以用 straight_join 写法固定连接方式，省去 mysql 优化器自己判断的时间。
 select * from t2 straight_join t1 on t1.a = t2.a;// 指定 mysql 选择 t2 表作为驱动表。
 注：straight_join 只适用于 inner join，left join、right join 已经制定了表的执行顺序（尽可能让 mysql 优化器去判断，除非很明确知道大小表）
 关联字段建索引

#### in、exists 优化：

原则：小表驱动大表
 **in：** 当 B表的数据集小于 A表的数据集时，in 优于 exists

```
select * from A where id in (select id from B);

```

**exists：** 当 A表的数据集小于 B表的数据集时，exists 优于 in
 将主查询 A 的数据，放到子查询 B 中做条件验证，根据验证结果（true/false）来决定主查询的数据是否保留。

```
select * from A where exists (select 1 from B where B.id = A.id)

```

#### count 优化：

count(1) > count(name) 约= count(*) > count(id)
 二级索引 count 速度略大于 count 一级索引
 因为一级索引中保存了所有数据，而二级索引中只保存了主键。
 count(1) 略快于 使用二级索引，因为 count(1) 直接 +1，不会取其中的值。
 count(*) 速度和 count(name) 差不多，都是走二级索引
 **注意：** count 二级索引的时候要注意必须为非 null 列，因为不会字段为 null 的列是不会计算进去的。
 mysql 5.7 之后，count(id) mysql 会自动优化走二级索引。因此速度都差不多。

```
explain select count(1) from employees;
explain select count(id) from employees;
explain select count(name) from employees;
explain select count(*) from employees;

```

四个 sql 的执行计划一样，说明这四个 sql 的执行效率应该差不多，区别在于根据某个字段 count 不会统计字段为 null 值的数据行。
 mysql 选择辅助索引而不是聚集索引的原因：因为二级索引相对主键索引存储数据更少，检索性能应该更高。
 推荐使用 count(*)

**常见优化方式：**
 1、查询 mysql 自己维护的总行数
 对于 **myisam 存储引擎** 的表做不带 where 条件的 count 查询性能是很高的，因为 myisam 存储引擎的表的总行数会被 mysql 存储在磁盘上，查询不需要计算
 对于 **innodb 存储引擎** 的表 mysql 不会存储表的总记录行数，查询 count 需要实时计算。
 2、show table status
 如果只需要知道表总行数的估计值可以用如下 sql 查询，性能很高
 `show table status like 'employees';`
 3、将总数维护到 Redis 里
 插入或删除表数据行的时候同时维护 redis 里的表总行数 key 的记数值（用 incr 或 decr 命令），但是这种方式可能不准，很难保证表操作和 redis 操作的事务一致性
 4、增加计数表
 插入或删除表数据行的时候同时维护计数表，让他们在同一个事务里操作。

Mysql 查数据/修改 数据，会先从磁盘中复制到 buffer pool 中，当修改时，并不是直接修改磁盘内容，而是修改 buffer pool 中的对应页的对应数据，然后在事务提交时，将修改的操作记录到 redo log（还会记录到 binlog，binlog 记录的是语句，而 redo log 记录的是内存中地址及要修改的内容，因此 redo log 恢复数据快于 binlog）。同时会记录 undo log，方便事务回滚时使用。定时去根据 redo log 更新到磁盘中。
 buffer pool 中对应页修改后，变成脏页

调优，如果硬件满足，可以调大 buffer pool（数据页存放在内存） 的大小，越大，性能越好。
